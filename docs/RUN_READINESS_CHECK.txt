赛题完整性与实例内运行就绪复审（直接项目执行方案）
更新：2026-11-03；当前starter-v4／模型测试r7／运行internal-v9-r2。

一、工作边界与结论

助手负责每个实例内部的安装、环境检查、模型部署、实验/评测运行及排错。
实例保存、镜像保存/复制和跨实例迁移等平台操作由用户自行负责，不属于本报告待办。
仍遵守联网CPU准备依赖、无网H200运行及指定路径；依赖安装不要求CPU挂载项目盘。
安装入口为scripts/prepare_cpu_h200.sh --dependencies-only。

六公开环境、可改LLM基础框架和九隐藏自动实验/配对提交/固定积分/评分已有本地闭环。
当前包已有校验记录；正式现场尚未全部验收。用户已明确正式评测直接运行各队当前
项目，测评期间禁止编辑代码/配置或改写所用权重。现有正式入口仍按旧容器方式受理，
因此尚未满足“接入九宇宙后在本队项目中用统一命令完成正式评分”。需补直接执行
适配、文稿与配置同步以及真实模型整轮验收，不能再声称缺少六公开或基础智能体。
逐队封装镜像、另复制队伍项目、容器模型挂载不作为用户新方案的必需步骤。

二、九宇宙评分流程及当前实现边界

1. 攻坚组保留约定程序入口和模型配置。窗口开始后停止编辑，由指挥部在该队当前项目
   目录直接启动，读取其已保存完成的实际模型。本步是最新确定方式，正式入口待适配。
2. 指挥部用该版本依次运行九宇宙；每个宇宙独立会话、配额和产物目录。
3. 智能体取得mission和第一束光，在600秒探索窗口内自主实验、拟合和检验候选。
4. 为当前宇宙自动生成law.py与三字段claims.json，通过save_draft/submit成对冻结。
5. 指挥部传入允许的隐藏测试初态和时刻，由law.py给出加速度，固定积分器生成预测
   轨迹，与无噪轨迹真值及预存声明真值比较，按既定80/15/5计分。
6. 超时取最后及时有效配对；无有效配对该界0分。基础设施故障另行处理。完成九界后
   汇总一次完整成绩，仅反馈总分和各宇宙总分，隐藏运行材料赛中不归还。

队员不在正式运行中手工补交规律或干预。六公开用于开发；九隐藏仍由智能体现场自动
实验，外层模型/程序提交与每界law/claims属于不同层次。
代码依据：contest_job_runner、contest_console_service、law_submission_store、
law_program_evaluation和contest_scoreboard（均为指挥部运行包文件）。

  逐字节一致，不含九隐藏真实场/真值/验证答案。

- 截止按成功受理时间、最佳整次成绩和同分加权节约分已有代码；人工受理次数控制
  是既定方案，不因本次检查要求另补程序计数器。
- 既有179项公开回归通过、2项平台跳过，以及15界75次合成HTTP联调。此为工程证据，
  不是本轮新模型成绩或真实白名单模型能力结论。

四、实际剩余事项

1. 发布文稿同步
   8页_更新版.docx的计分、600秒和噪声已同步，但缺六公开开发与九隐藏运行的明确分工；
   模拟器源码保密句应只针对九正式宇宙。实际starter的SUBMISSION_API.txt仍将
   examples/agent.py称为零加速度旧例，实际入口已转发shore_agent；技术规范还有
   starter-v2/31文件旧数。若干contracts把已实现功能列待办，应清理状态文字。

2. 直接项目正式入口与实际模型加载
   contest_platform受理仍要求镜像并核对镜像内清单；JobRunner明确拒绝正式队列采用
   诊断本地后端。需增加明确的直接项目正式模式，不能把local-diagnostic标志直接
   当正式成绩入口。旧诊断逻辑可复用，不等于新模式已经完成。
   manifest绝对模型路径仍限/models；需适配实际/inspire/...模型路径。直接启动还应
   使用队伍配置的解释器和必要环境，避免换成指挥部解释器或过滤掉推理所需配置。
   队伍可用原白名单及合法训练成果，包括完整checkpoint或底座+adapter；通过同一
   启动约定加载实际成果，不能因旧七预设部署工具限制而缩小白名单。

3. 正式配置和赛务口径冻结
   已有内部操作域、验证案例和资源值；正式公开范围/时域、验证范围和公开粒度、
   在线榜与终评案例关系仍须确认。内部样例不是已经发布的正式范围承诺。
   原profile仍internal_validation、批准false，各界仍标calibration_not_final。需为
   直接项目方式明确科学源/固定积分身份和发布核验，不把旧候选镜像/模型挂载字段当
   作新模式必需。启动/候选执行超时、CPU/内存等内部值须经现场检查后冻结。
   用户已提出四窗口、四次机会，具体排期与受理口径需统一公告；人工控制次数即可，
   不增加复杂窗口计数系统或因此修改评分规则。

4. 真实目标实例完整验收
   在实际Linux/H200和真实权重上验证依赖、加载、FP8/MoE/多卡、600秒发现质量，再完成
   六公开与九隐藏整轮。核对实际运行的是本队当前代码/配置/模型，固定积分、超时取
   最后有效稿、无稿0分、坏候选/指挥部故障分类及仅规定成绩反馈均符合规则。
   原configure/preflight/model-smoke/release-reviewed是既有容器流程工具，不将其整套
   当作直接项目方式的必经步骤；需按新方式完成相应检查。一次生成烟测不等于整轮。

5. 评测耗时与队列容量
   当前逐界启动智能体，基础框架可能重复加载大模型；须测冷启动、整轮时间及多队
   排队吞吐，不以600秒乘九替代实测。实际GPU占用按现场安排确认；若复用队伍卡，
   需在测评时释放相应资源，不能从“直接项目目录运行”推断已经分配了另一套GPU。
